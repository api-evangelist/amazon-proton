<h2>Introduction</h2> 
<p>Modern applications run on a variety of compute platforms in AWS including serverless services such as <a href="https://aws.amazon.com/lambda">AWS Lambda</a>, <a href="https://aws.amazon.com/apprunner/">AWS App Runner</a>, and <a href="https://aws.amazon.com/fargate/">AWS Fargate</a>. Organizations today are often required to support architectures using a variety of these AWS services, each offering unique runtime characteristics, such as concurrency and scaling, which can be purpose fit and optimized for a particular workload. As customers adopt these services using practices such as infrastructure as code (IaC) and continuous integration and continuous delivery (CI/CD) practices, they often face challenges with how to scale them within their organizations. In contrast to the original idea of the <a href="https://aws.amazon.com/devops/what-is-devops/">DevOps</a> <a href="https://docs.aws.amazon.com/whitepapers/latest/introduction-devops-aws/two-pizza-teams.html">two-pizza team</a> approach where a single team develops AND operates an application in production, we’ve seen new roles emerge in the industry such as DevOps engineer and platform engineer. These newer roles tend to be more focused on cloud infrastructure and operations work so that developers can focus on writing application code such as frontend graphical user interfaces (GUIs), backend APIs, and database queries. These newer DevOps and platform engineering roles are challenged with how to support many development teams with IaC and CI/CD. They want to ensure that development teams adhere to their organization’s standards and guidelines for security, reliability, and cost optimization, however, they don’t want to become bottlenecks as development teams need to move fast and deploy new services quickly. To help address these challenges, internal developer platforms (IDPs) are becoming increasingly popular as a mechanism to help platform engineers and development teams collaborate and move faster with increased reliability and consistency. If you’d like to learn more about how we’re seeing companies organize for modern cloud operations, please refer to <a href="https://aws.amazon.com/blogs/devops/how-organizations-are-modernizing-for-cloud-operations/">this post</a>.</p> 
<p>A significant challenge with employing IaC and CI/CD templates at scale is maintaining and evolving them over time. Tools that scaffold templates are great, but what happens when changes are needed? For example, suppose you have a template that provisions web applications using <a href="https://aws.amazon.com/pm/ecs">Amazon Elastic Container Service (ECS)</a> and <a href="https://docs.aws.amazon.com/AmazonECS/latest/userguide/what-is-fargate.html">AWS Fargate.</a> AWS releases a new capability such as Amazon <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect.html">ECS service connect</a> and you want to enable your template users to opt-in to this new capability. What if you’ve scaffolded dozens of CI/CD pipelines and later decide that you want to add a security scanning step? <a href="https://aws.amazon.com/proton/">AWS Proton</a> attempts to address these ongoing challenges by providing platform engineers with mechanisms to be able to version and track templates, and publish updates so that development teams can consume them. AWS Proton is a service that helps platform teams scale their impact by defining and updating infrastructure for self-service deployments. AWS Proton provides a managed deployment mechanism with a central dashboard providing template usage visibility and traceability across AWS accounts.</p> 
<p>AWS Proton can support a large variety of use cases; however, as an example, this post will show how AWS Proton can be used to provision containerized web application architectures running on Amazon ECS Fargate with CI/CD pipelines running on <a href="https://github.com/features/actions">GitHub Actions</a>. The IaC to provision the web application and CI/CD pipeline is encapsulated within a Proton service template that can be easily consumed by developers in a self-service fashion and maintained over time. This post will use <a href="https://github.com/aws-containers/proton-codebuild-provisioning-examples/tree/main/terraform#readme">sample AWS Protons templates</a> implemented using <a href="https://www.terraform.io/">Terraform</a> to provision and deploy a <a href="https://github.com/aws-samples/aws-proton-sample-services/tree/main/ecs-backend">sample Python Flask web application</a>. You’ll walk through how to publish and deploy two AWS Proton templates that provide developers with everything they’ll need to stand up a new web application in AWS and a CI/CD pipeline that builds and deploys their code.</p>

<h2>Walkthrough</h2> 
<h3>Template registration</h3> 
<p><img alt="Proton environment template registration step" class="aligncenter wp-image-13388" height="223" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Environment-Service.png" width="565" /></p> 
<p>To get started, you’ll need an environment in which to deploy a web app. The web application needs to accept traffic from the internet and possibly connect to internal resources such as an Amazon Relational Database Service (<a href="https://docs.aws.amazon.com/rds/?icmpid=docs_homepage_databases">Amazon RDS</a>) database running in a private subnet. In this post, you’ll use an AWS Proton <a href="https://docs.aws.amazon.com/proton/latest/userguide/ag-environments.html">environment template</a> that provisions an Amazon Virtual Private Cloud (VPC) network to accomplish this using the <a href="https://github.com/aws-containers/proton-codebuild-provisioning-examples/blob/main/terraform/environment-templates/tf-vpc-ecs-cluster/v1/README.md">VPC ECS Cluster</a> sample template. The first thing you’ll need to do is to register this template in your AWS account. You can clone the <a href="https://github.com/aws-containers/proton-codebuild-provisioning-examples/tree/main/terraform/environment-templates/tf-vpc-ecs-cluster/v1">sample repo</a> to your machine and register the environment template using the following commands. You’ll need to supply an Amazon Simple Storage Service (<a href="https://docs.aws.amazon.com/s3/?icmpid=docs_homepage_serverless">Amazon S3</a>) bucket that you can write to, which is used to store your template artifacts during registration. You can export an environment variable named S3_BUCKET or replace ${S3_BUCKET} in the following command. As an alternative, you can use AWS Proton’s <a href="https://docs.aws.amazon.com/proton/latest/userguide/ag-template-sync-configs.html">template sync</a> feature to automatically register templates from a Git repo. Template sync requires that you fork the repo into your own GitHub organization and use the <a href="https://docs.aws.amazon.com/proton/latest/userguide/setting-up-for-service.html#setting-up-vcontrol">AWS CodeStar connection</a> to access the repo and make it available to AWS Proton. You can read about the template sync feature <a href="https://docs.aws.amazon.com/proton/latest/userguide/ag-template-sync-configs.html">here</a>, but for now you’ll use Amazon S3 to do the registration.</p> 
<div class="hide-language"> 
 <pre><code class="lang-apacheconf">git clone git@github.com:aws-containers/proton-codebuild-provisioning-examples.git proton-examples

cd proton-examples/terraform/environment-templates/tf-vpc-ecs-cluster/v1
make template bucket=${S3_BUCKET} version=1
</code></pre> 
</div> 
<p>Next, you’ll register an AWS Proton <a href="https://github.com/aws-containers/proton-codebuild-provisioning-examples/blob/main/terraform/service-templates/tf-ecs-fargate-lb-service-cicd-gh-actions/v1/README.md">service template that provisions a load-balanced web application and a CI/CD pipeline</a> that can build and deploy containers from a source code repo.</p> 
<div class="hide-language"> 
 <pre><code class="lang-apacheconf">cd ../../../service-templates/tf-ecs-fargate-lb-service-cicd-gh-actions/v1
make template bucket=${S3_BUCKET} version=1
</code></pre> 
</div> 
<h3>Create environment</h3> 
<p><img alt="Create Proton environment step" class="aligncenter wp-image-13389" height="405" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Create-Environment.png" width="207" /></p> 
<p>Now that you’ve registered the templates, you can create a new instance of an environment. To do that, you’ll login into the <a href="https://docs.aws.amazon.com/awsconsolehelpdocs/latest/gsg/learn-whats-new.html">AWS Management Console</a>, navigate to AWS Proton, select <strong>Environments</strong>, select <strong>Create environment</strong>, and choose the <strong>Environment for</strong> <strong>ECS Fargate </strong>template. Note that the following walkthrough setup process uses the AWS Management Console; however, these actions can be automated using the AWS Command Line Interface (<a href="https://docs.aws.amazon.com/cli/?icmpid=docs_homepage_mgmtgov">AWS CLI</a>) or Application Programming Interfaces (APIs).</p> 
<p><img alt="Proton environment template selection" class="aligncenter wp-image-13437 size-medium" height="300" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/11/Environment-for-Fargate-1-292x300.png" width="292" /></p> 
<p>After entering an environment name of <em>dev</em> and an optional description, you’ll select your <a href="https://docs.aws.amazon.com/codebuild/?icmpid=docs_homepage_devtools">AWS CodeBuild</a> provisioning role. This role determines the scope of infrastructure that the environment template and the related service templates can provision. AWS Proton uses AWS CodeBuild as an environment in which to run your template commands. After selecting <strong>Next</strong>, AWS Proton allows you to specify input parameters for the environment template. For customers that prefer a graphical interface, it is important to point out that AWS Proton dynamically generates this user interface based on the <a href="https://github.com/aws-containers/proton-codebuild-provisioning-examples/blob/main/terraform/environment-templates/tf-vpc-ecs-cluster/v1/schema/schema.yaml">schema file included in your proton template</a>. For customers that prefer more of a <a href="https://aws.amazon.com/blogs/containers/tag/gitops/">GitOps</a> style of provisioning, AWS Proton supports a service sync capability that you can read about <a href="https://docs.aws.amazon.com/proton/latest/userguide/ag-service-sync-configs.html">here</a>. You can accept the template defaults, select <strong>Next</strong> again, and choose <strong>Create.</strong></p> 
<p><img alt="Enter Proton template inputs" class="aligncenter wp-image-13391 size-full" height="827" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Configure-Custom-Settings.png" width="977" /></p> 
<p>At this point, AWS Proton provisions your environment resources, which includes a VPC network, Amazon ECS Cluster, AWS IAM roles, and an Amazon S3 bucket to store the Terraform remote state. This example template happens to be built using Terraform; however, AWS Proton’s CodeBuild provisioning feature allows you to use any IaC tool (e.g., AWS Cloud Development Kit (CDK)) or scripts that you prefer.</p> 
<p>After a few minutes, AWS Proton has provisioned your dev environment by applying the template’s Terraform using AWS CodeBuild provisioning. When complete, the environment’s deployment status changes to <strong>Succeeded</strong> and you’re ready to deploy your web application into this environment.</p> 
<p><img alt="Proton environment summary" class="aligncenter wp-image-13392 size-full" height="691" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Environment-Summary.png" width="977" /></p> 
<h3>Create service, pipeline, and instance</h3> 
<p><img alt="Create service, pipeline, and instance step" class="aligncenter wp-image-13442 size-medium" height="300" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/11/Service-Pipeline-Instance-1-156x300.png" width="156" /></p> 
<p>To provision your web application and CI/CD pipeline, you’ll navigate to <strong>Services</strong>, then select <strong>Create Service</strong> and choose <strong>Load Balanced ECS Fargate Service with a GitHub Actions CI/CD Pipeline</strong>.</p> 
<p><img alt="ECS Fargate Service Template" class="aligncenter wp-image-13444 size-medium" height="295" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/11/Load-Balanced-ECS-300x295.png" width="300" /></p> 
<p>After entering a service name (e.g., <em>web-app</em>), you connect the service to a GitHub repository containing your application source code. You can use your own application repo; however, in this example you’ll use the <a href="https://github.com/aws-samples/aws-proton-sample-services">aws-proton-sample-services</a> repository by forking it into your GitHub organization or by creating a new repository from the repository template. When you choose the <strong>Link another Git repository</strong> option, you should be able to select GitHub, your <a href="https://docs.aws.amazon.com/codestar/?icmpid=docs_homepage_devtools">AWS CodeStar</a> connection and then select the repository and <strong>main</strong> branch.</p> 
<p><img alt="Create Proton service and link Git repo" class="aligncenter wp-image-13397" height="888" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Configure-Service.png" width="662" /></p> 
<p>Next, the wizard asks you to configure your AWS Proton service instances. You’ll create a single instance with the name <em>dev</em>, and select the AWS Proton environment named <em>dev</em>, which you created earlier. Since you’ll eventually be deploying the <a href="https://github.com/aws-samples/aws-proton-sample-services/tree/main/ecs-backend">ecs-backend</a> sample app, you’ll enter port 80 and a health check path of /ping since that’s how the sample application has been configured. The sample application is a very simple Python application that uses the <a href="https://flask.palletsprojects.com/">Flask web framework</a>. You’ll accept the template’s default public.ecr.aws/aws-containers/proton-demo-image container image that dynamically uses the selected port and health check. This image is updated and replaced by a new image that’s built in the next CI/CD pipeline job.</p> 
<p><img alt="Proton service instance input" class="aligncenter wp-image-13399" height="734" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Service-Instance.png" width="759" /></p> 
<p>For the AWS Proton Service’s Pipeline Inputs section, we’ll need a GitHub Personal Access Token (PAT) that allows the service to provide a GitHub Actions CI/CD pipeline by sending the workflow YAML file to our application repo. You can follow the <a href="https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/creating-a-personal-access-token">GitHub docs</a> to create a PAT with the <strong>workflow</strong> scope. After you’ve created the PAT, you add it to <a href="https://docs.aws.amazon.com/secretsmanager/index.html">AWS Secrets Manager</a> so that your AWS Proton service can consume it. To do this, open a new tab in the AWS Console, navigate to <strong>Secrets Manager</strong> and choose the <strong>Store a new secret</strong> option. Select <strong>Other type of secret</strong> and enter the GitHub PAT in the <strong>Plaintext</strong> tab. It should look something like the following.</p> 
<p><img alt="Create Secrets Manager secret" class="aligncenter wp-image-13400" height="523" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Choose-Secret-Type.png" width="835" /></p> 
<p>Next, name the secret <strong>github/token/sample-app</strong>, give it an optional description, then choose <strong>Next</strong>, <strong>Next</strong>, and <strong>Store</strong>.</p> 
<p>With the secret stored securely in Secrets Manager, you can go back to the AWS Proton tab and enter the name of the secret in the <strong>Pipeline inputs</strong> section. For <strong>Docker Path</strong> enter ./ecs-backend so that the proper sub-directory is built.</p> 
<p><img alt="Set Secrets Manager secret in Proton template input" class="aligncenter wp-image-13401" height="289" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Pipeline-Inputs.png" width="699" /></p> 
<p>After selecting the <strong>Next</strong> button, AWS Proton provisions the service template, which involves two main steps.</p> 
<ol> 
 <li>Provision the web application infrastructure for the service instance. This involves provisioning an Application Load Balancer and an Amazon ECS Service running the default container.</li> 
 <li>Provision the pipeline infrastructure. This includes provisioning an Amazon Elastic Container Registry (<a href="https://docs.aws.amazon.com/ecr/?icmpid=docs_homepage_containers">Amazon ECR</a>) repository, an AWS IAM role that GitHub Actions will assume, and a GitHub Actions workflow YAML file that’s sent to the application repository as a pull request (PR).</li> 
</ol> 
<h3>Run CI/CD pipeline</h3> 
<p><img alt="Run CI/CD pipeline step" class="aligncenter wp-image-13402" height="446" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Run-CICD-pipeline.png" width="357" /></p> 
<p>Once the AWS Proton service status changes to <strong>Active</strong> and the pipeline provisioning status changes to <strong>Succeeded</strong>, you should see the workflow PR URL appear in the outputs section of the pipeline tab. If you select that link, you’ll see a PR called <strong>Proton generated GitHub Actions CI/CD pipeline</strong>.</p> 
<p><img alt="Proton service pipeline output" class="aligncenter wp-image-13404" height="128" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Outputs.png" width="744" /></p> 
<p><img alt="GitHub pull request with CI/CD pipeline" class="aligncenter wp-image-13405" height="286" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Pipeline1.png" width="737" /></p> 
<p>When you merge this PR, GitHub Actions runs a workflow job that builds the Python application into a container image, pushes it to Amazon ECR, and updates the AWS Proton service to deploy the newly built image to your service instance.</p> 
<p><img alt="GitHub Action deployment" class="aligncenter wp-image-13406 size-medium" height="268" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Deploy-300x268.png" width="300" /></p> 
<p>Once the GitHub Actions workflow job is complete, you should see Amazon ECS rolling out a new deployment.</p> 
<p><img alt="ECS Fargate Rolling Deployment" class="aligncenter wp-image-13407 size-full" height="191" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/Deployments-GitHub.png" width="977" /></p> 
<p>When the Amazon ECS deployment is complete, you can select the endpoint located in the AWS Proton service instance output and you should see the Python application running. With this pipeline in place, future code commits that are pushed or merged to the main branch will trigger the pipeline.</p> 
<p><img alt="Running application endpoint" class="aligncenter wp-image-13408" height="183" src="https://d2908q01vomqb2.cloudfront.net/fe2ef495a1152561572949784c16bf23abb28057/2023/07/10/JSON.png" width="709" /></p> 
<p>Keep in mind that what’s shown above is just one workflow used as an example. The important thing is that this workflow is encapsulated within an AWS Proton service template that can be changed over time. A platform engineering team could also provide additional service templates with alternative workflows, or even allow template users to customize the workflow by specifying custom input parameters. An example of an alternative workflow might be to just trigger CI from GitHub PRs, building container images and pushing them to Amazon ECR. Deployments could be triggered in more of a GitOps approach using AWS Proton’s <a href="https://aws.amazon.com/blogs/containers/announcing-git-based-service-deployments-with-service-sync-for-aws-proton/">service sync</a> capability, which allow you to declaratively specify an AWS Proton service’s input parameters in a file that lives in a Git repository that AWS Proton watches and deploys for you. The key is that you have flexibility and can encapsulate your workflow inside of templates that can be versioned, tracked, and maintained over time.</p> 
<h3>Maintenance</h3> 
<p>While the CI/CD pipeline for each workload lives in the workload’s GitHub repo, AWS Proton provides a loosely coupled mechanism for development teams to stay in sync and up-to-date with standards and best practices set by platform teams. For example, let’s say that a few months after deploying a workload using your templates, your platform engineering team decides they want everyone to start running a new security scanning tool and only deploying if the scans pass. The platform engineering team can update the service template to include this new automation, publish a new version, and then either allow consuming teams to upgrade their templates at their leisure or update all environments or services at once using the AWS Proton API. The following screenshot shows how a developer might be notified that there’s a newer template version available that allows them to update to the recommended version. Selecting on this button triggers a deployment of the new pipeline, which results in another PR with the latest pipeline changes.</p>

<h2>Prerequisites</h2> 
<p>If you’d like to follow this walkthrough in your own AWS account, you’ll need to complete the <a href="https://docs.aws.amazon.com/proton/latest/userguide/getting-started-prerequisites.html">one-time AWS Proton setup prerequisites</a>, which includes setting up AWS Identity and Access Management (<a href="https://docs.aws.amazon.com/iam/?icmpid=docs_homepage_security">AWS IAM</a>) roles and an <a href="https://docs.aws.amazon.com/proton/latest/userguide/setting-up-for-service.html#setting-up-vcontrol">AWS CodeStar connection</a> to your GitHub account. This requires elevated AWS account permissions.</p> 
<h2>Cleaning up</h2> 
<p>If you’d like to remove the AWS resources created during the walkthrough, you can delete the AWS Proton service which will automatically delete all resources created by the service pipeline and instance. Once the service has been deleted, you can delete the AWS Proton environment which will delete the shared resources. The only exception is the Amazon S3 bucket created as part of the environment that holds the Terraform remote state. This bucket is not automatically deleted in case you need to restore any of the previous resources. You’ll need to manually empty and delete this bucket. Once the service and environment have been deleted, you can safely delete the AWS Proton service and environment templates.</p> 
<h2>Conclusion</h2> 
<p>In this post, we showed you one example of what you can build with AWS Proton templates. As a platform engineer, you’ve published AWS Proton templates that provide developers with everything they need to stand up a new web application in AWS and a CI/CD pipeline that builds and deploys their code. This enables your developers to be able to focus on building their app, while giving your platform teams a mechanism to provide guardrails and updates to their cloud resources and CI/CD pipelines over time. The value of AWS Proton is that you can encapsulate your infrastructure and pipeline rules and logic into a resource that is version-able, update-able, and traceable across your AWS accounts.</p> 
<p>You can browse the <a href="https://github.com/aws-containers/proton-codebuild-provisioning-examples">proton-codebuild-provisioning-examples</a> repository to see other example templates that use <a href="https://www.terraform.io/">Terraform</a>, <a href="https://github.com/aws-containers/proton-codebuild-provisioning-examples/tree/main/cdk">CDK</a> and <a href="https://github.com/aws-containers/proton-codebuild-provisioning-examples/tree/main/pulumi">Pulumi</a>. There’s also another <a href="https://github.com/aws-containers/proton-codebuild-provisioning-examples/tree/main/terraform/service-templates/tf-ecs-fargate-lb-service-cicd-codepipeline/v1">Terraform example template</a> that uses <a href="https://aws.amazon.com/codepipeline/">AWS CodePipeline</a> for CI/CD instead of GitHub Actions. With AWS Proton’s CodeBuild provisioning capability, you can build templates using whichever tooling you prefer. If you prefer <a href="https://docs.aws.amazon.com/cloudformation/?icmpid=docs_homepage_mgmtgov">AWS CloudFormation</a> as your IaC tool, then we also have sample templates published <a href="https://github.com/aws-samples/aws-proton-cloudformation-sample-templates">here</a>. We encourage you to try out the sample templates and provide feedback on the AWS <a href="https://github.com/aws/aws-proton-public-roadmap/projects/1">Proton public roadmap GitHub repo</a>.</p>
